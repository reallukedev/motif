# iOS: radio vs on-demand, 2026-09-08

Captured on a physical iPhone 17 Pro Max, iOS 27. Apple Music Chill, Apple Music 1, a
personal artist station, and an album (*emails i can't send*).

## The signal is the queue entry id

`MusicPlayer.Queue.Entry.id` has the form `<queue>::<item>`:

| Source | `entry.id` |
|---|---|
| Apple Music Chill | `Jzb4lWyve::STREAM` |
| Apple Music 1 → *Dai Dai* | `PxDIf4ejk::STREAM` |
| Prateek Kuhad station | `o6C8OJs7I::STREAM` |
| Album, track 1 | `PRhKeIIy0::6ostOUDHU` |
| Album, track 2 | `PRhKeIIy0::EHYCyckzc` |

The item half is the literal string `STREAM` for radio and an opaque identifier otherwise.
The queue half is constant within a queue and differs between stations, which is also how a
session boundary is detected.

This is stronger than the macOS signal: it *states* the source rather than inferring it from
a missing field. Undocumented, so it is isolated behind `QueueEntryIdentifier` with tests
carrying the real ids.

## Both prior hypotheses were wrong

- **`entry.isTransient` is `false` for radio**, the same as for an album. The idea that a
  server-driven queue would produce transient entries is dead.
- **`playParameters` reports `{"id":"…","kind":"song"}` for radio and on-demand alike.** No
  `radioStation` kind appears anywhere. This was the stronger of the two guesses.

Both are still dumped by the probe, and both are recorded in code as rejected, so the next
person does not spend an afternoon re-testing them.

## The macOS rule must not be ported

On iOS, MusicKit reports a real `Song.duration` for a radio track once the entry resolves:
*Dai Dai* came back as 223 seconds, with `MPMediaItem.playbackDuration` 223.0. The macOS
"no duration means radio" rule would therefore answer *on demand* for a station and be
wrong. Where an entry id exists it is the only thing consulted.

## Entries resolve in two stages

A queue entry appears twice, roughly a second apart:

```
13:42:12.840  entry.title "Apple Music 1"   item nil    playbackStoreID ""
13:42:13.858  entry.title "Dai Dai"         item song   song.id 6768469976

13:43:11.080  entry.title "Hallelujah…"     item nil    playbackDuration 0.0
13:43:12.153  entry.title "Hallelujah…"     item song   song.id 1087736468
```

Capturing the first stage would write the station itself into the playlist as a song, so an
unresolved entry is not treated as an observation at all. This is what the brief's "read
after a short delay" is actually about, and the delay is closer to a second than to the
300ms first guessed.

At a station change the unresolved title is the **station name** ("Apple Music Chill",
"Apple Music 1", "Prateek Kuhad"), which is the only source of one on iOS, mirroring macOS.

## Fields that discriminate nothing

`persistentID` (0 throughout), `mediaType` (0), `isCloudItem` (false), `hasProtectedAsset`
(false), `repeatMode`, `shuffleMode`. `playbackStoreID` is empty until the entry resolves and
then equals `song.id`, so it is a second route to the same catalog id, not a signal.

`MPMediaLibrary.authorizationStatus()` was `notDetermined` while MusicKit was `.authorized`.
The two are separate grants, and the MediaPlayer half was never needed.
